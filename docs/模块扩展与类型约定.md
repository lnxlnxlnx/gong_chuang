## 3. Optional 的使用边界

`Optional[T]` 与 `T | None` 表达同一种可空类型。用户新增的字段注解方向正确，问题不在这两种拼写之间。

| 场景 | 类型约定 | 原因 |
|---|---|---|
| `Robot` 按需开启的内部模块字段 | `Optional[具体模块类]` | 本次会话确实可能未启用该模块 |
| `Robot` 构造注入参数 | 与字段对应的具体可空类型 | review 能直接看到允许注入什么 |
| `robot.arm` 等公开属性 | 非空具体模块类 | 未启用或已关闭时抛错，上层取得对象后直接调用 |
| 初始化中或关闭后可能不存在的资源 | 具体可空类型 | 保留真实生命周期状态，在动作边界明确检查 |
| 构造结束后始终存在的依赖 | 非空具体类型 | 不因初始化方便而长期保留 Optional |
| 没有检测到物料、没有可用观测 | 保留现有结果中的 Optional | 这是业务数据语义，不应为了消除报错而改成异常或假数据 |

需要检查的是被使用的值本身。`self._borrowed`、`pose_state.is_known` 等布尔值，不会让类型检查器自动推断另一个字段已经非空。返回 `None` 的检查函数也不会自动把调用方的可空字段变成非空。

源码修订应保留项目原定的 Python 版本下限。下面示例采用 `Optional` 等写法；无需为统一拼写批量修改无关文件，也不提高 Python 版本要求。

## 4. Robot 的明确类型契约

影响位置：`robot.py` 的构造函数、模块属性、装配方法、抓取配置快照和清理回调。

以下是需要达到的签名与字段形状；现有 open/close、所有权和异常清理逻辑继续保留，不另建一套管理类。

```python
from __future__ import annotations

from typing import TYPE_CHECKING, Optional, TypeVar

if TYPE_CHECKING:
    from modules.arm.runtime import RobotArm
    from modules.chassis.runtime import MecanumChassis
    from modules.grasp.runtime import Grasp
    from modules.motor.drive.emm42 import SerialPort
    from modules.servo.runtime import GripperServo
    from modules.vision.runtime import Vision

T = TypeVar("T")


class Robot:
    def __init__(
        self,
        *,
        arm: Optional[RobotArm] = None,
        gripper: Optional[GripperServo] = None,
        vision: Optional[Vision] = None,
        chassis: Optional[MecanumChassis] = None,
        grasp: Optional[Grasp] = None,
        bus: Optional[SerialPort] = None,
    ) -> None:
        """保存已装配模块；bus 的现有总所有者约定保持不变。"""
        self._arm: Optional[RobotArm] = arm
        self._gripper: Optional[GripperServo] = gripper
        self._vision: Optional[Vision] = vision
        self._chassis: Optional[MecanumChassis] = chassis
        self._grasp: Optional[Grasp] = grasp
        self._bus: Optional[SerialPort] = bus
        self._owns_bus = bus is not None
        self._closed = False

    def _module(self, name: str, value: Optional[T]) -> T:
        """检查会话与模块状态，成功时返回确定存在的对象。"""
        self._require_open()  # 沿用现有关闭状态检查。
        if value is None:
            raise RuntimeError(f"本次会话没有启用 {name}")
        return value

    @property
    def arm(self) -> RobotArm:
        return self._module("arm", self._arm)

    @property
    def gripper(self) -> GripperServo:
        return self._module("gripper", self._gripper)

    @property
    def vision(self) -> Vision:
        return self._module("vision", self._vision)

    @property
    def chassis(self) -> MecanumChassis:
        return self._module("chassis", self._chassis)

    @property
    def grasp(self) -> Grasp:
        return self._module("grasp", self._grasp)
```

注解专用的导入放在 `TYPE_CHECKING` 内，真实装配需要的导入保留在原装配边界。不能只为添加注解，就在导入 `Robot` 或构造一个部分模块的会话时加载其他设备后端。

其他需要具名的类型：`modules` 返回模块名元组；`on_message` 为可选的 `Callable[[str], None]`；串口工厂返回 `SerialPort`；`_attempt` 的 action 为 `Callable[[], None]`，errors 为 `List[Tuple[str, Exception]]`。清理集合若需要公共接口，仅声明含 `close() -> None` 的窄 `Closable` 协议；模块字段和属性仍保留具体类。

`Robot.open` 中配置预读得到的可空局部变量，要在装配点通过实际值检查或返回非空值的校验函数缩窄。不能仅凭此前另一个布尔变量为真，就把 `Optional[ArmConfig]`、`Optional[VisionConfig]`、可空端口等传给必需参数。

### 4.1 抓取配置快照固定为具名结构

`Robot._load_grasp_settings` 当前返回裸 `dict`，再以 `**grasp_settings` 注入。保持这条简单装配链，只为这五个固定字段定义精确 `TypedDict`：

```python
from typing import Optional, TypedDict

from modules.grasp.drive.servo_model import (
    LiftScale,
    ObjectSelector,
    ServoConfig,
    ServoJacobian,
    ServoTarget,
)


class GraspSettings(TypedDict):
    """已通过普通抓取动作前置校验的配置快照。"""

    config: ServoConfig
    selector: ObjectSelector
    target: ServoTarget
    jacobian: ServoJacobian
    lift_scale: Optional[LiftScale]
```

该类型放在 `modules/grasp/runtime.py`，供该模块和 `Robot` 共用。target/Jacobian 的原始加载结果仍允许缺失；进入这份快照前，必须明确检查并取得非空值，同时保留原有雅可比奇异校验。之后构造函数、`_from_modules_settings` 与动作字段使用非空 `ServoTarget`、`ServoJacobian`。校准工具仍使用原来的可空加载结果，不因本次类型修订强制要求已标定。

## 5. 各模块需要补齐的类型边界

| 位置 | 当前问题 | 必须达到的结果 |
|---|---|---|
| `modules/arm/runtime.py::_advance_pose` | 先检查 `is_known`，随后把可空 pose 当成确定对象 | 对局部 pose 明确判空；原位姿未知时仍不推进，也不凭空造坐标 |
| `modules/servo/runtime.py::__init__` | 通过 `_borrowed` 间接判断 servo，导致 `_servo` 被推断为可空 | 直接判断 `servo is not None`；两个分支结束后 `_servo` 为确定的驱动类型 |
| `modules/vision/runtime.py` | `_camera`、`_locator` 只初始化为 None；读取方法缺返回类型 | 字段标明真实资源类型；就绪助手检查后返回非空资源，动作使用返回的局部变量；`_read_report` 返回 `Optional[Tuple[MaterialReport, float]]` |
| `modules/grasp/runtime.py` | 配置、注入参数和部分动作返回类型不明确；`_arm/_source` 初始为空 | 配置与注入贯穿具名类型；动作使用明确非空资源；`align_xy` 明确返回现有 `ServoResult` |
| `modules/motor/drive/emm42.py::SerialPort` | write 协议与真实 pyserial 的位置参数和返回类型不兼容 | 改为 `write(self, data: bytes, /) -> Optional[int]`，匹配实际位置调用及可空返回值；不用 cast 掩盖 |

`emm42.py` 当前只执行 `serial_port.write(frame)`，随后 flush，并按既有设置读取 ACK，未消费 write 的返回值。因此本次只修正协议声明；验证短写或拒绝 None 会改变发送行为，不混入类型修订。现有返回 int 的假串口仍满足该协议。

Grasp 算法取观测继续复用已有 `FrameSource` 协议，不复制 Vision 的全套接口。会话持有的 `_source` 还需要关闭能力；在现有 `modules/grasp/drive/servo_observation.py` 的 `FrameSource` 旁只增加下面这个窄协议：

```python
class ClosableFrameSource(FrameSource, Protocol):
    """支持观测与关闭；是否拥有资源仍由会话装配决定。"""

    def close(self) -> None: ...
```

该文件已有 `Protocol` 导入。`Grasp._source` 标为 `Optional[ClosableFrameSource]`，`source_factory` 标为 `Callable[[], ClosableFrameSource]`，`modules/grasp/test/manual/align_xy.py::_open_source` 同步返回 `ClosableFrameSource`。这样 Vision、CameraLink 与满足协议的离线替身都可注入，工厂到字段之间不会丢掉关闭能力。动作算法仍只要求 `FrameSource`；`from_modules` 当前借用的视觉参数仍明确为 `Vision`，借用分支不关闭它。仅能调用 close 不等于拥有资源，所有权仍由原装配逻辑决定。

所有缩窄都保持现有业务结果：Vision.locate 无画面仍报错、没有物料仍返回空报告；frame 的无观测仍按既有协议处理；普通抓取缺 target/Jacobian 仍在打开设备前失败。类型修订不改变回零、坐标定义、运动顺序、脉冲或标定参数。

不使用 `Any`、`object`、`cast`、`type: ignore` 或关闭诊断来让这些边界“通过”。第三方库内部不能保证完全有类型，但本项目公开注入、属性、配置快照和结果不能因此退回未知类型。

## 6. 新设备的最小接入约定

新模块继续使用独立 `runtime.py` 放上层接口，驱动与通信放 `drive/`，包根明确导出上层类。沿用既有 `open(...)`、`close() -> None`、上下文管理与资源所有权约定；动作参数和结果有明确类型。业务动作按设备本身设计，不为统一外观添加无用途的方法。

每次新增设备，以下接入点必须同步接受 review：

| 接入面 | 验收目标 |
|---|---|
| 模块自身 | 可独立开启、调用和关闭，不要求先构造完整 Robot |
| Robot 入口 | 有具名构造字段、非空具体类型属性、明确的 open 选择参数和配置路径 |
| 配置与装配 | 需要的配置在开设备前校验；装配使用同一份已校验快照 |
| 模块清单 | `modules`、`open_all`、`ALL_MODULES` 的含义一致，无遗漏 |
| 生命周期 | 成功时逆序释放；中途失败也释放已取得资源；借用者不关闭所有者的连接 |
| 上层示例 | main/test 仅选择模块、取得对象、调用动作，不导入底层驱动或手动拼串口 |
| 离线验证 | 覆盖该设备单独选择、组合选择、实例复用和开关次数 |

当前 `ALL_MODULES` 只是常量，尚未驱动其他分支，新增名称不会自动完成接入。这里采用少量具名位置显式维护，不为两个待接入设备改成动态注册。

### 6.1 托盘：先区分独立设备还是共享舵机总线

未来的“托盘”不能直接等同于现有 `TurntableServo`。具体驱动要等电机/舵机、通信方式和动作含义明确后再定，不在本文填写硬件参数。

如果托盘确实与夹爪共用当前舵机总线，则连接所有权是接入前必须解决的条件：

- `Robot` 取得一条舵机连接，夹爪与托盘按不同 ID 借用；最终由 `Robot` 关闭一次。
- 单独使用某模块时，该模块可自行取得并拥有连接；注入连接时必须按借用处理。
- 现有 `BusServo.close` 会关闭注入的串口，`TurntableServo` 也还没有新版借用生命周期，必须在接入时明确修正；仅多加一个 `robot.tray` 字段不能解决同口打开与互相关闭。
- 复用已有夹爪/转盘 ID 冲突校验。若实际是独立设备，则按独立连接装配，不预先引入共享总线。

### 6.2 GM65：独立扫码模块，明确协议后接入

当前没有 GM65 实现。先明确实际通信方式、触发方式、报文边界与输出编码，再确定驱动。上层通过具名 `robot.scanner` 取得扫码对象，读取方法的返回类型、等待参数和失败语义在该设备设计中一次说清。

不预设串口号、指令、超时值或自动切换通信模式；不把扫码解码逻辑塞进 Robot。Robot 只负责配置校验、装配和生命周期。

## 7. 后续源码修订的验收标准

1. 第 2 节命令对六个入口报告零错误；不靠关闭诊断、忽略注释或把类型扩大为 Any 达成。
2. IDE/检查器明确识别五个 `robot.<模块>` 属性的具体类。有效动作和参数通过，拼错方法名、错误参数类型、`Robot(arm=123)` 能在静态检查时被拒绝。相关反例只用于离线类型验证，不执行设备。
3. 未启用模块和已关闭会话仍立即报错；上层无需对每次取得的模块反复判空，也不会在访问属性时偷偷打开设备。
4. Vision/Grasp 的资源、配置、回调与返回结果有明确类型。正常可空业务结果保留，必需动作依赖在进入动作前已确定非空。
5. arm/chassis 仍使用同一连接，grasp 仍使用同一个 arm/vision；现有实例身份测试继续通过。注解不能替代实例身份和所有权测试。
6. 一个端口只打开和关闭一次；借用模块关闭不影响其他模块。中途开启失败时，已取得资源均被尝试释放，重复 close 不再发设备命令。
7. 新设备单独选择时不打开无关设备；加入 open_all 后其失败不能静默跳过。源码示例和模块清单与实际选择项保持一致。
8. 类型修订保持现有公开动作、单位和异常语义，并保持导入时不打开设备或加载模型。验证只使用静态检查与离线替身，不运行真机入口。

**实施结果：**第 1–8 条均已满足。补充两条实施说明：

- `Grasp._require_action_ready` 现在**返回**缩窄后的 `(target, jacobian)`；`_open_settings` 与
  `_from_modules_settings` 两处接缝各自再查一次（纵深防御）：公开入口已经先查过，
  但绕过公开入口直接调接缝、或由 `Robot` 传入快照时，空值仍会在装配前被拦住——
  原来的"缺 target/Jacobian 零设备"测试因此继续有效，不需要改测试意图。
- `Robot._owns_bus` 的开位不变量两处都要维持：构造注入 `bus` 时按"借来的"处理，
  `open` 里**自己开**那条连接之后必须显式置为所有者，否则总关闭会漏掉它。

第 6 节的托盘与 GM65 **仍未实现**：它们需要先确定电机/舵机、通信方式与动作含义；
`ALL_MODULES` 目前只是常量，新增名字不会自动完成接入。
