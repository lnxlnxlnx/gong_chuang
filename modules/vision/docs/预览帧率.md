# 预览帧率：慢在哪、怎么改的、还能怎么调

这份文档回答一个问题：**"摄像头帧率不高"到底是摄像头的、YOLO 的，还是 OpenCV 的？**
结论按实测数据给出，并说明为此改了什么、没改什么。

测量机：Windows 笔记本（RTX 4060，但 OpenCV 是 `pip opencv-python`，**没有 CUDA**，
推理走 CPU），摄像头 1280×720 USB，图像用 `models/dataset/images/train/*.jpg`
（真实台面图）与 `models/top_pic.png`。全部用 `time.perf_counter` 取平均。

## 一、先量一遍：每一段各花多少

| 环节 | 实测 | 是瓶颈吗 |
| --- | --- | --- |
| 摄像头取帧（1280×720, MJPG/MSMF） | **27–30 fps**（33–37 ms/帧） | 不是。三种后端/四种设置组合都是 27–30 fps |
| YOLO 推理（ONNX → OpenCV DNN，CPU，320×320 输入） | **17–20 ms** | 不是。50 fps 的量级 |
| `cv2.imshow` + `waitKey(1)`（720p） | **3.5–7 ms** | 不是 |
| 字母箱预处理（720p → 320×320） | 1.4 ms | 不是 |
| `MaterialLocator.locate()`：霍夫路径 | **780–3300 ms** | **是** |
| `MaterialLocator.locate()`：颜色块路径 | **470–2540 ms** | **是** |

所以答案是：**都不是**。摄像头跑满，YOLO 只占 20 ms；
**慢的是经典 CV（霍夫圆 / 颜色块）那一段**，外加一个把所有环节串成一条线的循环。

## 二、慢的三个原因

### 1. 串行循环：显示帧率 = 1 /（取帧 + 推理 + 画图 + 显示）

原来的预览是：

```
frame = camera.read()      # 阻塞等一帧
hits  = detector.detect(frame)   # 阻塞算完
cv2.imshow(...); cv2.waitKey(1)
```

任何一段慢，整条链路一起慢。更糟的是**取帧从来没有停过**：驱动缓冲区里越积越多，
画面看着卡、延迟还越来越大——手在镜头前动一下，窗口里要过一秒才动。

### 2. 每个候选圆都把整帧重转一次灰度图（12 ms × 24–87 个候选）

`MaterialLocator._face_qualities` 对每个候选圆调一次 `measure_face`，
而 `measure_face` 每次都 `to_grayscale(frame)`——1280×720 的 BGR 转 float64
**实测 12.0 ms**。霍夫在真实台面图上会给：

| 图 | 候选圆 | 只算这一项 |
| --- | --- | --- |
| black (1).jpg | 24 | 349 ms |
| black (248).jpg | 87 | **993 ms** |

转出来的灰度图逐帧、逐候选都是同一张，纯粹白花。

### 3. 同一帧问两遍模型；颜色块路径上 `minEnclosingCircle` 卡住

- 调色板没命中 → 问一次模型 → 退回霍夫 → 因为 `hits` 是空又**再问一次模型**：
  同一个 frame、同样的参数，结果必然一样，白花约 20 ms。
- `ColourBlobLocator.blob_shape` 用 `cv2.minEnclosingCircle` 算外接圆半径。
  OpenCV 这个函数点数一多就急剧变慢（实测同一条轮廓：3862 点 **826 ms**、
  1931 点 110 ms、966 点 14.5 ms、483 点 2.1 ms）。`models/top_pic.png` 一帧
  954 ms 里有 **826 ms** 全花在这一行上。

## 三、改了什么

### 1. 取帧与推理各跑一条线程（`modules/vision/drive/stream.py`）

- `FrameGrabber`：后台线程不停 `read()`，**只留最新一帧**，旧帧直接丢。缓冲区不再积压，
  显示的是"现在"而不是"刚才"。
- `DetectionWorker`：后台线程对最新一帧跑推理。忙的时候新帧**顶掉**待处理帧（不排队），
  所以推理永远算最新的画面，不会一路追赶旧帧。
- `run_preview()`：显示循环只做"拿最新帧 → 用最近一次结果标注 → `imshow` + `waitKey(1)`。
  窗口因此跑在**摄像头帧率**上，推理按自己的速度跑。
- 窗口左下角写着一行 `cap / det / ms / age`：

  ```
  cap  29.8 fps | det   6.2 fps   160 ms | age   90 ms
  ```

  `cap` 是摄像头实际帧率，`det` 是识别实际帧率，`ms` 是最近一次推理耗时，
  `age` 是画面上那组框比当前画面旧了多少毫秒。**"画面卡"与"识别慢"从此是两个可分辨的数。**
- 标注的是**最新帧**、框可能略旧（`age` 就是它），这是有意的取舍，写在画面上而不是藏起来。
- **抓取控制链路不要用 `run_preview`**：它需要"结果与画面严格同帧"，请直接同步调
  `locator.locate(frame)`。`run_preview(async_detect=False)` 是原来的串行行为。

### 2. 去掉每帧的重复计算（数值完全不变）

- 灰度图**一帧只转一次**，而且"用到才转"（没有候选圆时一次都不转）；
  `to_grayscale` 对已经是 float64 的灰度图**原样返回、不再复制**。两遍（严格参数 +
  放松参数）共用同一张。
- 模型**一帧只问一次**。
- 轮廓送进 `minEnclosingCircle` 之前**等间隔抽样**到 256 点以内。

### 3. `main.py` 的物料预览改用 `config.json` 的 `targets`

`modules/vision/app/demo.py::demo_material` 现在和菜单 18 一样读
`targets.material_palette` / `material_bgr` / `working_distance_mm` /
`color_tolerance` / `material_diameter_mm`。这三个参数决定"用颜色块还是霍夫找圆"
以及"半径窗口按物理先验算还是按画幅猜"，之前 `main.py` 一个都没用上，
于是默认入口跑的是最慢、也最不稳的那条路。

## 四、改完的效果（同一台机器、同一批图）

| 路径 / 图 | 改前 | 改后 | 倍数 |
| --- | --- | --- | --- |
| 霍夫路径 black (1).jpg | 1249 ms | **182 ms** | 6.9× |
| 霍夫路径 black (76).jpg | 1184 ms | **155 ms** | 7.6× |
| 霍夫路径 black (248).jpg | 3324 ms | **634 ms** | 5.2× |
| 霍夫路径 black (275).jpg | 782 ms | **99 ms** | 7.9× |
| 颜色块路径 black (1).jpg | 842 ms | **193 ms** | 4.4× |
| 颜色块路径 black (76).jpg | 720 ms | **170 ms** | 4.2× |
| 颜色块路径 black (248).jpg | 2543 ms | **471 ms** | 5.4× |
| 颜色块路径 black (275).jpg | 469 ms | **162 ms** | 2.9× |
| `top_pic.png`（真实物料照片） | 954 ms | **131 ms** | 7.3× |

数值不变已逐项核对：`measure_face(BGR 帧) == measure_face(转好的灰度图)` 在
4 张真实图的 24/18/87/17 个候选上**逐位相等**；`minEnclosingCircle` 抽样后外接圆
半径变化 < 0.15%（判据阈值 0.65，实测物料 0.74–0.96、同色结构件 0.36–0.53，
差这 0.15% 挪不动任何一次判定）。

**显示侧**：窗口从"跟着最慢那段走"变成跟着摄像头走。`python -m modules.vision.drive.stream`
的自测用假摄像头（60 fps）与假推理（50 ms）把这件事量出来：显示 51–60 fps、
推理 20 fps、跟不上的帧被跳过；把 `async_detect=False` 换回串行，显示立刻塌到 19 fps。

## 五、还嫌慢时看这里

1. **先看窗口左下角的 `det`**：如果是 5 fps 上下而 `cap` 是 30，说明瓶颈还在识别侧，
   下面是可调的；如果 `cap` 本身就低，那是摄像头/线材/被别的程序占用。
2. **配上物料颜色**（`targets.material_palette`）：走颜色块定位，不再靠霍夫在整幅
   1280×720 上凑圆。这是"稳"和"快"的最大一个开关。
3. **把 `targets.working_distance_mm` 收窄到真实机位**（例如实际 70–90 mm 就写
   `[70, 90]`，不要写 `[55, 160]`）：半径窗口越准，霍夫凑出来的假圆越少。
   实测 black (248).jpg：窗口 95–276 px 时 55 个候选、43.6 ms；
   收窄到 120–220 px 只剩 9 个候选、18.8 ms。
4. **没有物料在画面里时最慢**：这时严格参数找不到"像顶面的圆"，算法会**再跑一遍
   放松参数的霍夫**（这是有意的精度设计，126–267 ms），然后还要给上百个假圆各量一次
   顶面质量。实测最坏一帧 471–634 ms 基本都在这里。
5. 想再快只能改识别本身（把检测放到低分辨率上跑、或改匹配规则），那会**改变识别结果**，
   属于另一件事：颜色块路径的 4 个调色板颜色每帧要做 4 遍全帧颜色距离
   （26 ms × 4 ≈ 107 ms），这一项没动，因为它一改就会影响"哪些块算物料"。

## 六、刻意没改的

- **`HoughRingLocator` 的检测参数与半径窗口**（`param1` / `param2` / `dp`）：
  它们决定"锁定哪个圆"，改了就是改识别结果。速度问题用"别重复算"和"别阻塞显示"解决，
  不动判据。
- **颜色匹配规则**（BGR 距离 + 色相/亮度两条或关系）：同上。
- **抓取链路**（`modules/grasp`）：那里要的是结果与画面同帧，仍然是同步 `locate()`。

真机自测入口：
`python -m modules.vision.drive.stream`（两条线程的时序）、
`python -m modules.vision.drive.material_face`（灰度与顶面判据）、
`python -m modules.vision.drive.material_blob`（颜色块与轮廓抽样）、
`python -m modules.vision.drive.hough_lock`（霍夫圆）。
